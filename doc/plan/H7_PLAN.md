# H7 plan: COI filter mode, signal level

*Status: plan, awaiting approval. Branch: `ms/H7-coi-filter` (from `dev` @ H1c). Effort: 2–3 d.*

## Goal
`<coi file="…" mode="filter"/>` prunes the search *before* mining. For each consequent, antecedent propositions whose signals cannot structurally influence it are never tried. This is GoldMine-style mining: faster, and with no out-of-cone antecedents. It assumes the RTL is correct, so trivergence should use it only as a baseline (see TRIVERGENCE_IMPACT, H7–H9).

## Findings from the investigation (2026-10-05)
- **F1. Two places to prune.**
  - **Plain templates** (`G(P0 -> X P1)`): a permutation fixes every placeholder, so after `TemplateImplication::genPermutations` the permutations with an out-of-cone antecedent proposition can be removed. They are then never evaluated.
  - **Decision-tree templates** (`{..#1&..}`): the antecedent is built by `AntecedentGenerator` after the consequent permutation is loaded (`TLMiner::l1Handler`), so the out-of-cone candidates (`candidateVariables`, `numericCandidates`) are removed before the tree is built.
- **F2. The planned oracle does not hold for decision trees.** The PLAN's acceptance 1 says that filter output equals rank output post-filtered with `coiFrac == 1`. For plain templates it does. For decision trees it doesn't, because the tree is greedy:
  - `runDecisionTree` ranks candidates by gain and keeps the best (effort `E`), so removing an out-of-cone candidate can let an in-cone branch be explored that rank mode never explored;
  - `getMinimizedSolution` and known-solution dedup also depend on what else was found.

  So filter mode can find in-cone assertions that rank mode misses. That is a feature of pruning, but it breaks the equality.
- **F3. An oracle that does hold for both.** For each consequent proposition `c`, run **rank mode** on a configuration restricted *by hand* to:
  - consequent domain `{c}`;
  - antecedent and decision-tree propositions = only those in `c`'s cone.

  The union of these runs must equal filter mode's output. The decision tree then sees the same candidates in the same relative order (`std::sort` on the same gain sequence gives the same result), so the equality is exact.
  - **Independent:** the restricted configurations are produced by a separate Python script from `coi.json`, not by HARM's filter code.
  - **Limit:** it needs a single consequent placeholder per template. Templates with two (e.g. `camellia`'s `X(P1 && X[23] P2)`) are covered by acceptance A2 only.
- **F4.** HARM has no `coi.json` for `bl_master` or other examples (no RTL is shipped), so performance is measured on the 5 H4 fixtures. The report gives search-space sizes, not just times, since the fixtures are small.

## Decisions to approve
### D-017: what "in the cone" means for filtering
- **Proposal: exactly D-014's leaf rule,** so that filter and rank modes agree.
  - An antecedent proposition is in the cone of a consequent if **every** variable of the proposition is a source of **some** consequent variable.
  - A signal that `coi.json` marks unknown counts as in the cone (it cannot be excluded).
  - A consequent with an unknown variable keeps every antecedent: its cone is unknown.
  - Propositions without variables (constants) are kept.
- Placeholders that appear in both antecedent and consequent (`loc="ac"` in one template) are not filtered.
- Signal level only: depths are H8.

### D-018: filter mode and ranking
- **Proposal: in filter mode, HARM still computes `coiFrac`, `coiDepthFit` and `coiUnknown`,** so `<sort exp="coiDepthFit"/>` works in both modes. After filtering, `coiFrac` is always 1 (a check, see A3), and `coiDepthFit` still ranks by depth until H8 filters on it.

## Scope
1. `ManualDefinition`: accept `mode="filter"`, and print the one-time warning: "COI filter mode assumes the RTL is correct: behaviour removed or added by an RTL bug cannot be mined (use mode="rank" for bug hunting)".
2. `CoiInfo`: `inCone(proposition, consequentVariables)` (D-017), shared with `computeCoiMetrics`, so that rank and filter use one definition.
3. `TemplateImplication`: remove the out-of-cone permutations after `genPermutations` (plain templates).
4. `TLMiner::l1Handler`: remove the out-of-cone decision-tree candidates (propositions and numerics) for the loaded consequent.
5. **Statistics** (info messages, and `"coiFilter"` in `--dump-assertion-info`): per template, the permutations before and after; for decision trees, the candidates before and after (summed over consequents); and the mining time.

## Validation (independent)
- **A1:** the restricted configurations come from a separate script reading `coi.json`, and HARM runs them in rank mode, without filter code. A pruning bug, or an over-pruning bug, shows up as a set difference.
- **The cones themselves** were validated by simulation in H4.
